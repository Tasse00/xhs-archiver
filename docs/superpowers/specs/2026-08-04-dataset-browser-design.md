# 数据集浏览页 — 设计文档

配套阅读：`2026-08-03-xhs-archiver-design.md`（主设计文档，唯一权威）。本文只描述浏览页，与主文档冲突时以主文档为准。

## 1. 目标

在一个独立标签页里翻看数据仓库里已经采集的内容：有哪些数据集、每个数据集里有哪些笔记、每篇笔记的正文图片评论长什么样、数据完不完整。

面向的是「采完一批之后核对质量」这件事，不是给外部看的展示界面。

## 2. 范围

**做：** 只读浏览。目录树、笔记列表、笔记详情、图片查看、评论查看、搜索、排序、按采集者筛选。

**不做：**

- **任何写盘操作。** 不删除、不移动、不改归属、不重新采集。浏览页拿到的是只读权限（`queryPermission({mode: 'read'})`），从能力上就写不了
- **不提供「重选数据仓库目录」。** 重选仍然只在侧边栏。两个地方都能改 root 会让「现在连的是哪个目录」变得说不清，而这个页面本来就是只读的
- **不做导出与统计面板。** 主文档 §11 把它们排在 v3，本文不提前
- **不做文件监听。** FSA 没有这个能力，见 §5.6

## 3. 入口

侧边栏顶栏加一个图标按钮，挂在刷新按钮旁边，只在配置完成（`configured` 为真）后显示。点击行为：

1. `chrome.tabs.query` 找有没有已经打开的浏览页
2. 有就 `chrome.tabs.update({active: true})` 激活它
3. 没有才 `chrome.tabs.create({url: chrome.runtime.getURL('src/browser/index.html')})`

不这么做的话点几次就是几个重复标签页，而它们各自持有一份内存缓存，纯属浪费。

不加 `contextMenus` 入口，不声明 `options_page`（除非 §7 的打包方案退到备选）。

## 4. 页面结构与交互

三栏：左目录树 | 中笔记列表 | 右详情栏。详情栏可关闭，关闭后列表占据其空间并多显示几列。

### 4.1 顶栏

仓库名 · 当前范围面包屑 · 搜索框 · 采集者筛选下拉 · 列显示开关 · 详情栏开关 · 重新加载。

「重新加载」与 §5.4 的「扫描」是两件事，措辞上要分清：**重新加载**清空内存缓存并重建树（应对 `git pull`），**扫描**是为排序/搜索读取当前范围的全部元数据。

### 4.2 左：目录树

节点就是目录。`全部` 之下按数据集路径的实际层级展开——`collected/2026-08-03` 是叶子，`collected` 是中间层；路径改成 `research/2026-Q3/outfit` 也一样成立，代码里不写死层级数。

每个节点显示篇数。**这个数字来自「目录里有多少个子目录」，不读任何文件**，所以树永远秒开，跟仓库总量无关。

**采集者不是树上的一级。** 采集者身份存在指针文件和 `note.json` 里，要在树上显示各人的篇数就得把全库读一遍，树就不能秒开了。它改为顶栏的筛选下拉，属于 §5.4 的显式扫描动作。列表里每行照常显示采集者——那是懒读顺带拿到的，不额外花钱。

### 4.3 中：笔记列表

表格行，固定行高 44px，虚拟滚动。

详情栏打开时（窄）显示：缩略图、标题、作者、点赞、收藏、评论、采集时间。
详情栏关闭时（宽）追加：分享、图片数、采集者、落盘路径。

互动数四项各占一列、右对齐，表头点击按该列排序。**砍列的顺序**是先砍详情栏里也有的那些，保证标题在任何宽度下都读得完整。

**「已采评论」是可选列，默认关，与栏宽无关。** 点赞/收藏/评论总数都在 `note.json` 里，一次读取全拿到；但「实际采到 18 条」只存在 `comments.json` 里，把它放进列表意味着每行读两个文件，行的填充成本翻倍。默认它只在详情栏出现；在顶栏手动打开后，无论详情栏开关它都显示，并且滚动会明显慢一档。

键盘：`↑` `↓` 换选中行，`Enter` 开详情，`Esc` 关详情。

### 4.4 右：详情栏

主图 + 缩略图条 · 标题 · 正文 · 话题标签 · 作者 · 四个互动数 · 发布时间 / 编辑时间 / IP · 采集信息（采集者、采集时间、第几次采集、落盘路径）· 评论列表（含子评论与配图）。

`✕` 或 `Esc` 关闭。`↑` `↓` 换行时详情跟着变。栏宽可拖拽，宽度存 `localStorage`（纯视图偏好，不属于采集设置，没必要进 `chrome.storage`）。

点任意一张图进全屏看图器，`←` `→` 翻图，`Esc` 退出。**原图只在看图器里才解码**（见 §5.3）。

### 4.5 详情栏里的数据质量提示

这三条是核对数据集时真正想知道的事，成本都只有一两次 IO，且只在点开某一篇时才付：

| 提示 | 判据 |
|---|---|
| 「这篇还被 X 采过」/ 并发采集竞态警告 | `lookup(store, noteId)` 返回多于一个指针。见主文档 §6.4 |
| 「未登记到索引」 | 目录在、指针不在。说明当时是 `partial` 状态没写指针 |
| 「N 张图片文件缺失」 | `note.json` 的 `images[]` 里有条目在磁盘上找不到对应文件 |

## 5. 数据来源与大数据量策略

前提：仓库当前几百篇，未来可能几万篇。要求是实现别太重。

### 5.1 成本在哪

| 动作 | 代价 |
|---|---|
| 列目录 | 极低。一次调用拿回整个目录的名字数组 |
| 读一个 `note.json` | 中。约 1~3 ms。1 万篇全读 = 十几秒 |
| 解码一张原图 | 高。原图 2~5 MB，解码后占内存十几倍 |

**目录树需要的信息全部来自「列目录」，一个文件都不用读。** 真正贵的元数据和图片，只有屏幕上那几十行需要。整个策略就建立在这条上：**开页成本与仓库总量无关**。

### 5.2 三层懒加载

1. **树**：只列目录。开页即出，篇数准确
2. **范围**：选中节点 → 收集其下所有叶子 → 每个叶子列一次目录 → 得到 `NoteRef[]`（`{noteId, datasetPath}`）。纯字符串，5 万条也就几 MB
3. **行**：滚进视口才读 `{datasetPath}/{noteId}/note.json`，一次拿全标题、作者、四个互动数、图片数、封面文件名、采集信息、正文与标签（后两者供搜索用）。读到的存进 `Map<noteId, RowMeta>`，会话内不重读

默认排序是「数据集名倒序，组内按目录名」。日期形态的目录名天然就是时间倒序，零成本且稳定，不需要读任何文件就能定序。

### 5.3 缩略图

读封面文件 → `createImageBitmap(blob, {resizeWidth: 96, resizeQuality: 'low'})` → OffscreenCanvas → `convertToBlob` → objectURL。**原始 blob 立刻丢弃，只留 96px 那份**（行高 44px，96 是给 2x 屏留的余量）。

objectURL 进 LRU（上限 300 条），淘汰时 `URL.revokeObjectURL`。这是整个功能里唯一会吃内存的地方，不这么做撑不过几屏。

详情栏的缩略图条用 `resizeWidth: 320`，同样走 LRU。看图器才读原图，退出时立刻释放。

读取走并发上限 6 的队列，滚出视口的任务直接丢弃——快速拖滚动条时不会排起几百个 pending。

### 5.4 排序、搜索、采集者筛选是显式动作

这三件事都需要当前范围的**全部**元数据，做不到懒加载。所以它们是显式的：点下去先弹一句「需要读取 128 篇」，带进度条和取消按钮（`AbortSignal`），扫完把 `Map` 填满并给该范围打上 `scanned` 标记。之后在同一范围里再排再搜是纯内存操作，瞬时。

扫描中途读失败的不中断，扫完汇总「N 篇读取失败」并可展开看是哪几篇。

搜索匹配标题、正文、作者昵称、话题标签，大小写不敏感的子串匹配。不做分词、不做模糊匹配——这是团队内部核对用的工具，`includes` 足够。

**为什么不建持久缓存层。** 曾考虑开页全量扫描 + IndexedDB 缓存，让搜索排序瞬时。但 FSA 想做真正的增量更新得靠文件 mtime，而拿 mtime 必须 `getFile()`——等于还是把全库读了一遍，增量根本省不掉钱。结果是既背上缓存与磁盘对账的复杂度和 bug，又没换来开页速度。也曾考虑采集时顺手维护一份全库 `manifest.json`，但那直接推翻主文档 §4.2 的核心决策：单一文件多人写必然 Git 冲突。

### 5.5 数据集叶子的判定

一个目录如果它的子目录名**全都是 note_id 形态**，它就是数据集叶子；否则是中间层，继续往下展开。

note_id 形态：`/^[0-9a-f]{16,32}$/`（实测真实 id 为 24 位小写 hex）。

**判定只看名字，不去 `exists('note.json')` 验证。** 验证要对每个子目录多一次 IO，几万篇就是几万次。代价是万一有人手工往数据集目录里塞了个 hex 名字的空目录，它会作为「读取失败」的一行出现——这比慢十几秒可接受。

树遍历排除 `_index`、`.git` 以及所有文件条目。

### 5.6 外部改动

FSA 没有文件监听。`git pull` 拉来同事的新数据后页面不会自己知道。顶栏放一个「重新加载」按钮，点了清空内存缓存、重建树。

不做轮询——轮询等于每隔几秒把树重建一遍，白烧 IO 换一个几乎用不上的实时性。

## 6. 模块划分

核心层不碰 DOM 和 chrome API，依赖全部注入，可在 Node 下跑 Vitest（沿用项目约定）。

### 6.1 核心层新增

| 文件 | 职责 |
|---|---|
| `core/store.ts` | 增补 `listEntries(path): Promise<{name, kind}[]>`。`listDir` 原样保留，现有调用方不受影响 |
| `core/browse/tree.ts` | `buildTree(store)` → `DatasetNode[]`。中间目录与数据集叶子的判定在这里 |
| `core/browse/scope.ts` | 节点 → `NoteRef[]`；各排序比较器 |
| `core/browse/row-meta.ts` | 读 `note.json` → `RowMeta`；另一个函数读 `comments.json` 拿已采条数 |
| `core/browse/search.ts` | 内存里的过滤与排序 |
| `core/browse/virtual.ts` | `visibleRange(scrollTop, viewportHeight, rowHeight, total, overscan)`，纯函数 |

`visibleRange` 单独拎出来是因为虚拟滚动最容易错的就是边界（首尾、总数为 0、容器高度变化），做成纯函数才测得动。

### 6.2 数据形状

```ts
interface DatasetNode {
  path: string;        // 相对 root，如 collected/2026-08-03
  name: string;        // 末段
  isDataset: boolean;  // 叶子
  count: number;       // 自身笔记数 + 子树之和
  children: DatasetNode[];
}

interface NoteRef { noteId: string; datasetPath: string }

type RowState =
  | { kind: 'pending' }
  | { kind: 'ready'; meta: RowMeta }
  | { kind: 'error'; reason: string };
```

`RowMeta` 从 `note.json` 取，含标题、正文、标签、作者昵称、四个互动数、图片数与封面文件名、`archive` 全部字段、发布与编辑时间。**不保留 `raw`**——它是 `note.json` 里最大的一块，只为归档 diff 稳定性而存在，浏览页一个字段都用不上，留在内存里几万篇会白吃几百 MB。

### 6.3 UI 层

新目录 `src/browser/`：`index.html` / `main.tsx` / `App.tsx`；组件 `Tree` `Table` `DetailPane` `Lightbox` `ScanProgress` `PermissionGate`；hook `useThumbnail`（并发队列 + LRU + revoke）与 `useScope`。

参数：行高 44px，overscan 8 行，缩略图并发 6，LRU 300。

### 6.4 样式

把 `src/sidepanel/panel.css` 里那套 token 抽到 `src/styles/tokens.css`，侧边栏与浏览页各自 import。深浅主题两套值本来就在里面，抽出来两边自动保持一致。

**这是唯一一处会改动现有代码的地方**（除了顶栏加按钮和 `Store` 增补方法）。

## 7. 构建与接线

crxjs 只自动打包 manifest 里声明过的 HTML，而这个页面不属于 popup / side_panel / options 任何一种。

**方案：加到 `vite.config.ts` 的 `build.rollupOptions.input`。** 语义干净，页面就是页面。侧边栏按钮走 `chrome.runtime.getURL('src/browser/index.html')`。

**备选：** 若实现时发现 crxjs 对额外 input 的产物路径有意外，退到声明 `options_page`——零配置，还白送一个 `chrome://extensions` 里的入口，代价是「选项」这个词名不副实。这是实现细节，不影响设计。

manifest 权限不变：`tabs` 已有，句柄从 IndexedDB 取，不需要新权限。

## 8. 错误处理与边界

### 8.1 权限

新标签页里从 IndexedDB 取回句柄后 `queryPermission({mode: 'read'})`。浏览页只读，不请求 readwrite。

没授权就整页显示一个「授权访问数据仓库」按钮——`requestPermission` 必须由用户手势触发，页面加载时自动调用不会生效。

从未配置过 root 时显示「请先在侧边栏选择数据仓库目录」，不在本页提供选择器（见 §2）。

### 8.2 单篇的问题不能拖垮整个列表

| 情况 | 表现 |
|---|---|
| `note.json` 缺失或 JSON 损坏 | 该行显示为错误行（note_id + 路径 + 原因），其他行照常 |
| 封面图文件不在 / 解码失败 | 占位图标，不算错误 |
| `comments.json` 不存在 | 详情栏显示「未采集评论」。这是正常状态，不是错误 |
| 图片文件少了几张 | 画廊对应位置占位，详情栏顶部提示「N 张图片文件缺失」 |
| 数据集目录里混进非笔记目录 | 名字不符合 §5.5 的形态，直接不计入，不报错 |
| 仓库还是空的 | 空态：「还没有采集过笔记」 |
| 扫描时几篇读失败 | 不中断，扫完汇总「N 篇读取失败」，可展开看是哪几篇 |

## 9. 测试策略

核心层全部用现有的 `tests/helpers/memory-fs.ts` 驱动，不需要浏览器：

- 树构建：多级中间目录、空目录、混入的脏目录名、只有 `_index` 的仓库
- 范围展开：单叶子、多叶子、根节点
- 排序比较器：各字段、稳定性
- `RowMeta` 解析：正常、缺字段、JSON 损坏
- 搜索匹配：标题/正文/作者/标签命中，大小写
- `visibleRange`：首尾边界、总数为 0、overscan、容器高度变化

**`memory-fs.ts` 需要一处改动：** `MemDir` 现在把子项存在名为 `entries` 的 Map 字段上，而 `listEntries` 要用真实 FSA 的 `dir.entries()` 异步迭代器拿 `kind`——名字冲突。把内部 Map 改名为 `children`，并补一个 `async *entries()`。

不给 canvas、blob、objectURL 写单测——在 Node 下要 mock 一整套 Web API，收益不抵成本。它们进人工验收清单：缩略图正确释放（滚几千行后内存不涨）、快速拖滚动条不卡、看图器翻页、详情栏拖宽后刷新仍记得。

## 10. 与既有决策的关系

本设计不推翻主文档任何已定决策：

- 不引入本地缓存层，磁盘仍是唯一真相源（主文档 §4.2）
- 不引入单一汇总文件（主文档 §4.2「为什么不用单一 index.json」）
- 不执行任何 git 命令
- 不写盘，因而与「指针存在 ⟹ 数据完整」不变量无关

主文档 §11 把「采集历史列表」排在 v2、「统计面板 / 导出」排在 v3。本页面覆盖了 v2 的浏览部分；导出与统计仍留在 v3，本文不提前。
