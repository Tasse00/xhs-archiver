# 删除已采集的笔记 —— 设计

日期：2026-08-07

本文是 `2026-08-03-xhs-archiver-design.md` 的补充，覆盖一件事：**让使用者在插件里删掉一篇采错的笔记**，侧边栏与浏览页各一个入口。

与主设计文档冲突时，本文在这个范围内为准，其余一律以主设计文档为准。本文推翻了
`2026-08-04-dataset-browser-design.md` §8.1 的「浏览页只读」，见第 5 节。

---

## 1. 目标与动机

采错笔记是常态：点开一篇随手采了，之后发现不该收。现在唯一的补救办法是去数据仓库里手动删——
而且**要删两个地方**：笔记目录 `collected/<date>/<note_id>/`，以及索引指针
`_index/<bucket>/<note_id>/<collector>.json`。

这两处分居仓库两端，指针路径还要先算 bucket。实际发生的是：**目录删了，指针忘了删。**

留下孤儿指针的后果不只是"有个没用的文件"。它直接破坏仓库的核心不变量——
**「指针存在 ⟹ 数据完整」**：

- 自己再打开那篇，侧边栏查重命中指针，显示「你采过这篇」，但数据其实没了
- 别人 pull 之后同样命中，于是**放弃采集一篇仓库里根本不存在的笔记**

所以删除必须由插件来做，且必须两处一起删。这是本功能存在的全部理由。

## 2. 删除什么

**删掉这篇笔记在仓库里的全部痕迹。** 具体是：

| 删什么 | 从哪儿来 |
|---|---|
| 该 `note_id` 下的**全部**指针，不管采集者是谁 | `_index/<bucket>/<note_id>/*.json` |
| 这些指针各自 `path` 指向的目录 | 指针的 `path` 字段，去重 |
| 浏览页当前正在看的这一份目录 | 调用方传入的 `here`，可能是没有指针的孤儿副本 |
| 因此变空的父目录 | 见 §4.3 |

**为什么按 `note_id` 一网打尽，而不是只删眼前这一份：** 使用者的心智是「这篇我不要了」，
不是「这个目录我不要了」。仓库里同一篇存成多份（并发采集竞态、迁移中断留下的孤儿副本）
本来就是异常状态，删一次只清掉一份、剩下的还在，等于让人重复劳动而且不知道要重复几次。
代价是在浏览页 A 目录点删除时可能连带删掉 B 目录里的另一份——所以确认清单必须**逐条列出
将删的目录路径**，让这件事在按下去之前就看得见。

**明确不做：**

- **批量删除**。当下的诉求是「误采了一篇」，多选删除是另一个量级的交互（跨范围选择、
  部分失败怎么报），等真有批量清理需求时再单独设计。
- **回收站 / 软删除**。数据仓库是 git 仓，已 commit 的内容随时能恢复；没 commit 的
  本来就是使用者自己刚采的。而且 FSA 没有 move，"移到 `_trash/`" 要逐文件读写一遍
  （配图动辄几十 MB），并且 `_trash` 会被 git 跟踪，等于让垃圾永久进历史。
- **撤销**。理由同上。

## 3. 核心模块 `src/core/delete.ts`

两个函数，侧边栏与浏览页共用。与 `src/core/` 下其余模块一样不碰 DOM 和 `chrome.*`。

```ts
export interface DeletePlan {
  noteId: string;
  /** 将被删除的笔记目录，去重后按字典序排。 */
  dirs: string[];
  /** 将被删除的指针。 */
  pointers: Pointer[];
}

/** 只读，用来渲染确认清单。here 是浏览页当前这份目录，侧边栏不传。 */
export function planDelete(store: ReadStore, noteId: string, here?: string): Promise<DeletePlan>;

export interface DeleteResult {
  dirs: number;
  pointers: number;
}

export function deleteNote(store: Store, plan: DeletePlan): Promise<DeleteResult>;
```

**为什么拆成"先算计划、再执行"两步**：确认清单要显示的正是将删的东西，让 UI 自己去凑这份
清单等于把删除范围的定义抄两遍，两边迟早不一致。`planDelete` 的产物既是给人看的清单，
也是 `deleteNote` 的唯一输入——**看到的就是删掉的**。

`planDelete` 只声明 `ReadStore`：它确实不写盘，签名放宽后侧边栏和浏览页都能用，也让
"它不会误删"这件事由类型保证。

## 4. 执行顺序 —— 这是本设计最要紧的一条

### 4.1 先删指针，再删目录

这是 `archive()`「先写数据、后写指针」（主设计文档 §7）的镜像，理由完全相同：
**中断时的残留必须落在安全的那一侧。**

| 顺序 | 中断后留下 | 后果 |
|---|---|---|
| **先指针后目录**（采用） | 孤儿目录 | 安全。`quality.ts` 的 `no_pointer` 正是为它准备的，浏览页看得见；查重不受影响，重采会直接覆盖 |
| 先目录后指针 | 孤儿指针 | **破坏「指针存在 ⟹ 数据完整」**。所有人的查重都会拿到假阳性——正是本功能要消灭的那个问题 |

先删指针，最坏情况只是留下一堆文件；先删目录，最坏情况是污染整个团队的查重结果。
不对称得很明显，没有权衡余地。

### 4.2 步骤

1. 逐个删除 `plan.pointers` 对应的指针文件（`removePointer`）
2. 指针目录 `_index/<bucket>/<note_id>/` 若已空，删掉；桶目录 `_index/<bucket>/` 若也空了，一并删
3. 逐个删除 `plan.dirs`（`removeDir`，递归）
4. 清理因此变空的父目录，见 §4.3

`store.removeFile` / `removeDir` 已经吞掉 `NotFoundError`，所以「指针指向的目录早就
被手动删过了」这种情况天然安全——那恰恰是最常见的入口场景。

### 4.3 空父目录的清理边界

删掉 `collected/2026-08-04/<note_id>/` 后，若 `collected/2026-08-04/` 变空就删掉它。
但**只上溯一层，且路径不足三段就不动**——与 `archiver.ts` 现有的 `removeEmptyParent`
同一条规则（那里是迁移后清理，语义一致）。

守卫的用处：写入路径被设成 `collected` 这种两段路径时，笔记目录是
`collected/<note_id>/`，其父就是 `collected/` 本身。删空它没有意义，而且下次采集还要
重建。绝不会上溯到仓库根。

实现上把这段逻辑从 `archiver.ts` 提到 `delete.ts` 导出，`archiver.ts` 改为引用——
同一条规则不该有两份实现。

## 5. 浏览页拿完整 `Store`

`2026-08-04-dataset-browser-design.md` §8.1 把浏览页定位成只读，靠模块边界保证：
所有模块参数类型只写 `ReadStore`，权限门只申请 `mode: 'read'`。

**这条现在推翻。** 浏览页的定位从「只读浏览器」改成**数据仓库的管理中心**——删除是第一个
管理动作，后面还会有别的。为一个已经不成立的定位保留边界，只会让每个新功能都要先绕一次。

改动：

- `PermissionGate` 改申请 `readwrite`，直接复用 `handle-store` 的 `hasPermission` /
  `ensurePermission`，不再自己写 `MODE = { mode: 'read' }`
- `App` 保留完整 `Store`，往下传给 `DetailPane`
- **`src/core/browse/*` 的签名一律保持 `ReadStore` 不变**。那些模块（扫描、搜索、
  排序、行元数据、质量检查）确实不写盘，放宽签名不会带来任何好处，只会丢掉一层免费的保证

顺带说明一件早就成立的事实：句柄本来就是侧边栏用 `readwrite` 取得的**同一个**，
`queryPermission({mode:'read'})` 从来没有把它降权。所以这次改的是**声明**，不是能力——
浏览页在能力上一直都能写。

## 6. 顺带的小重构：`lookup` 放宽到 `ReadStore`

`index-store.lookup` 目前用 `store.listDir`，因此要求完整 `Store`。`quality.ts` 只好
自己重写一份只读版 `readPointers`，那里留着一句注释：「代价是十来行重复」。

把 `lookup` 改成用 `listEntries`（`ReadStore` 就有），签名放宽到 `ReadStore`：

- `quality.ts` 的 `readPointers` 直接删掉，改用 `lookup`
- `planDelete` 也用它，不必再造第三份
- `archiver.checkNote` 传的是完整 `Store`，放宽是兼容改动，调用点不动

## 7. 界面

### 7.1 确认用内联展开块，不用弹窗

两边统一：点「删除这篇」→ **原地展开**一块确认区，列出将删的目录路径与指针（采集者名），
下面两个按钮「确认删除」/「取消」。

**为什么不用 modal：** 浏览页已经有两处抢 `Escape`——`App` 用它关详情栏，`Lightbox`
用它关看图器。再塞一个 modal 就是三方打架，得引入一套焦点与优先级管理，为一个确认框不值。
而侧边栏本来就窄，modal 在那里也不好使。

**为什么不用 `window.confirm`：** 它显示不了清单。而清单是这个确认框存在的理由——
§2 说过，「可能连带删掉别处那一份」这件事必须在按下去之前看得见。

### 7.2 侧边栏

- 入口出现在**任何存在指针的状态**：`mine`（你采过）和 `others`（别人采过）都有。
  与采集/更新按钮同处底部动作区，样式是次要的危险色按钮，不与主按钮争视觉重量。
- 采集进行中（`progress !== null` 或 `pageStep !== null`）时禁用。
- 确认清单由 `planDelete(store, noteId)` 现算，不传 `here`——侧边栏只知道指针，
  不知道仓库里有没有别的孤儿副本，也不该为此扫全仓库。
- 删完重新走一遍判定：状态回到 `ready`（可采集），顶部给一条「已删除」结果卡，
  与现有的采集结果卡同一位置、同一套样式，切换到别的笔记后消失。

### 7.3 浏览页

- 入口在详情栏里，任何一行都能删——包括没有指针的孤儿副本、`note.json` 读不出来的错误行。
  正是这些行最需要清理。
- 确认清单由 `planDelete(store, noteId, noteKeyOf(ref))` 现算，**传 `here`**。
- 删完之后（使用者要能明确感知这一篇没了）：
  1. 那一行从列表移除
  2. **详情栏关闭**
  3. 左侧目录树对应节点的计数减一
  4. 列表区顶部给一条「已删除《标题》」的提示条
- **不重扫仓库。** 局部改 `refs` 即可。重扫的代价是每删一篇等一次全量扫描，而且
  `scanned` 标记作废，排序与搜索都要重来——连着清理几篇时这个代价无法接受。

## 8. 错误处理

| 情况 | 表现 |
|---|---|
| 权限在删除途中被回收（`NotAllowedError`） | 侧边栏进 `need_permission`（现有路径）；浏览页在确认块里报「授权已失效，请重新授权」。`isPermissionError` 已有 |
| 仓库目录整个没了（`NotFoundError`） | `store` 把它吞成「没有这个条目」，删除会安静地"成功"而什么都没删。侧边栏每个判定周期已经探 `rootExists`，下一轮就会进 `missing_root`；浏览页的 `PermissionGate` 挂载时探过，这里不额外加探测 |
| 部分删除失败（其他异常） | 冒到 UI，报出错原因，并说明**指针已删、数据目录可能有残留**——因为顺序保证了残留只会是孤儿目录，这句话永远成立 |
| 确认块打开期间数据被别处改了 | 不管。清单是打开那一刻算的，执行时 `removeDir`/`removeFile` 对已消失的条目本来就是空操作 |

## 9. 测试

**`planDelete`**（`tests/core/delete.test.ts`，用 `tests/helpers/memory-fs.ts`）：

- 没有指针、只有一个孤儿目录（传 `here`）→ 计划里有该目录、无指针
- 单指针、单目录 → 各一
- 同一目录下多个采集者的指针 → 多指针、目录去重成一个
- 指针指向两个不同目录 → 两个目录都进计划
- 指针指向的目录已不存在 → 仍进计划（执行时是空操作）
- `here` 与指针指向的目录相同 → 不重复计入

**`deleteNote`**：

- 删完后指针目录与桶目录都不再存在
- 桶目录下还有别的笔记时，桶目录保留
- 父目录变空 → 被删；父目录下还有别的笔记 → 保留
- 路径只有两段时不删父目录（不碰 `collected/` 本身）
- **顺序断言**：注入一个在 `removeDir` 抛错的 store，断言指针已全部删掉、目录仍在——
  即残留是孤儿目录而不是孤儿指针

**界面**：侧边栏与浏览页各一组，覆盖「入口在什么状态下出现」「点开后清单内容正确」
「确认后调用 `deleteNote` 并带上正确的计划」「取消后什么都不做」。浏览页额外断言
删除后详情栏关闭、该行从列表消失。

## 10. 已知代价

- **同一篇存成多份时会一次删光。** 这是刻意的（§2），清单会列出来，但使用者若不看清单
  就点确认，可能删掉他本想留下的那一份。接受：这种多份状态本身就是要清理的异常。
- **浏览页丢掉了「模块边界保证不写盘」这层保护。** 换来的是它能承担管理职责。
  `src/core/browse/*` 仍守着 `ReadStore`，保护并没有全丢。
- **删除不可撤销。** 恢复靠 git，前提是使用者有在 commit。README 里已经说明数据仓库
  应当是 git 仓库，这里不额外提醒。
