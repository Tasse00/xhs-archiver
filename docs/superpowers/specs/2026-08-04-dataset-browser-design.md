# 数据集浏览页 — 设计文档

配套阅读：`2026-08-03-xhs-archiver-design.md`（主设计文档，唯一权威）。本文只描述浏览页，与主文档冲突时以主文档为准。

## 1. 目标

在一个独立标签页里翻看数据仓库里已经采集的内容：有哪些数据集、每个数据集里有哪些笔记、每篇笔记的正文图片评论长什么样、数据完不完整。

面向的是「采完一批之后核对质量」这件事，不是给外部看的展示界面。

## 2. 范围

**做：** 只读浏览。目录树、笔记列表、笔记详情、图片查看、评论查看、搜索、排序、按采集者筛选、数据质量提示。

**不做：**

- **任何写盘操作。** 不删除、不移动、不改归属、不重新采集
- **不提供「重选数据仓库目录」。** 重选仍然只在侧边栏。两个地方都能改 root 会让「现在连的是哪个目录」变得说不清
- **不做导出与统计面板。** 主文档 §11 把它们排在 v3，本文不提前
- **不做文件监听。** FSA 没有这个能力，见 §5.7

**「只读」是模块边界保证的，不是平台能力保证的。** 见 §8.1。

## 3. 入口

侧边栏顶栏加一个图标按钮，挂在刷新按钮旁边，只在配置完成（`configured` 为真）后显示。点击行为：

1. `chrome.tabs.query` 找有没有已经打开的浏览页
2. 有就 `chrome.tabs.update({active: true})` 激活它
3. 没有才 `chrome.tabs.create({url: chrome.runtime.getURL('src/browser/index.html')})`

不这么做的话点几次就是几个重复标签页，而它们各自持有一份内存缓存，纯属浪费。

不加 `contextMenus` 入口，不声明 `options_page`（除非 §7 的打包方案退到备选）。

## 4. 页面结构与交互

三栏：左目录树 | 中笔记列表 | 右详情栏。详情栏可关闭，关闭后列表占据其空间并多显示几列。

### 4.1 顶栏

仓库名 · 当前范围面包屑 · 搜索框 · 采集者筛选下拉 · 列显示开关 · 详情栏开关 · 重新加载。

「重新加载」与 §5.5 的「扫描」是两件事，措辞上要分清：**重新加载**清空全部内存缓存并重建树（应对 `git pull`），**扫描**是为排序/搜索读取当前范围的全部元数据。

### 4.2 左：目录树

节点就是目录。`全部` 之下按数据集路径的实际层级展开——`collected/2026-08-03` 是数据集叶子，`collected` 是中间层；路径改成 `research/2026-Q3/outfit` 也一样成立，代码里不写死层级数。判定规则见 §5.6。

每个节点显示**候选笔记目录数**。这个措辞是准确的：数字来自「目录里有多少个名字符合 note_id 形态的子目录」，没有读文件验证过，所以一个恰好符合形态的空目录也会被计进去。真正的错误要等这一行的元数据被读取后才暴露，那时它会显示为错误行（§8.2）。

树的构建有成本，不是免费的，见 §5.2。

**采集者不是树上的一级。** 采集者身份存在指针文件和 `note.json` 里，要在树上显示各人的篇数就得把全库的文件读一遍。它改为顶栏的筛选下拉，属于 §5.5 的显式扫描动作。列表里每行照常显示采集者——那是懒读顺带拿到的，不额外花钱。

### 4.3 中：笔记列表

表格行，固定行高 44px，虚拟滚动。

详情栏打开时（窄）显示：缩略图、标题、作者、点赞、收藏、评论、采集时间。
详情栏关闭时（宽）追加：分享、图片数、采集者、落盘路径。

互动数四项各占一列、右对齐，表头点击按该列排序。**砍列的顺序**是先砍详情栏里也有的那些，保证标题在任何宽度下都读得完整。

**「已采评论」是可选列，默认关，与栏宽无关。** 点赞/收藏/评论总数都在 `note.json` 里，一次读取全拿到；但「实际采到 18 条」只存在 `comments.json` 里，把它放进列表意味着每行读两个文件，行的填充成本翻倍。默认它只在详情栏出现；在顶栏手动打开后，无论详情栏开关它都显示，并且滚动会明显慢一档。

键盘：只有 `Enter` 开详情，**换行靠点行**（点行同时打开详情栏）。

`Esc` 与 `↑` `↓` 都归看图器：列表与看图器都在 `window` 上监听，事件不从对方冒泡而来，谁也拦不住谁，两边同时响应的结果是——`Esc` 关一张图连详情栏一起关掉，`↑` `↓` 在看图时换掉整篇笔记、正在看的图当场消失。让给看图器比把看图器的开关状态提到 `App` 再逐键判断简单得多。

### 4.4 右：详情栏

主图 + 缩略图条 · 标题 · 正文 · 话题标签 · 作者 · 四个互动数 · 发布时间 / 编辑时间 / IP · 采集信息（采集者、采集时间、第几次采集、落盘路径）· 评论列表（含子评论与配图）· 数据质量提示。

`✕` 关闭（`Esc` 不关，见 §4.3）。点另一行时详情跟着变。栏宽可拖拽，宽度存 `localStorage`（纯视图偏好，不属于采集设置，没必要进 `chrome.storage`）。

点任意一张图进全屏看图器，`←` `→` 翻图，`Esc` 退出。**原图只在看图器里才解码**（见 §5.4）。

IP 属地在 `NoteRecord` 里没有顶层字段，只能从 `raw.ipLocation` 取。详情加载时单独提取这一个值，不保留整份 `raw`（见 §6.3）。

### 4.5 数据质量提示

核对数据集时真正想知道的事。判定需要读 `lookup(store, noteId)`（一次目录列举 + 一两次小文件读），只在点开某一篇时才付。

**判据必须比对物理路径，不能只看指针存不存在。** 同一个 note_id 可能有指针，但指向另一个目录——那时当前这个目录仍然是孤儿。记 `here = ${datasetPath}/${noteId}`，`ps = lookup(noteId)`：

| 状态 | 判据 | 提示 |
|---|---|---|
| 正常 | `ps` 恰有一条且 `path === here` | 无 |
| 无指针 | `ps` 为空 | 「当前目录没有对应的索引指针」 |
| 指针指向别处 | `ps` 非空但没有一条 `path === here` | 「索引里这篇指向 `X`，当前目录是遗留副本」 |
| 竞态：路径分叉 | `ps` 中出现两个以上不同的 `path` | 「N 个采集者的指针指向不同目录，需人工清理」（主文档 §6.4） |
| 竞态：同路径多人 | 多条 `path === here` 但 `collector` 不同 | 「N 个采集者都登记了这份数据」 |
| **不变量破裂** | 有 `path === here` 的指针，但 `note.json` 读不出或 `images[]` 里有文件缺失 | **最醒目的警告**：「指针存在但数据不完整」 |

最后一行单独强调，是因为主文档的「指针存在 ⟹ 数据完整」是整个查重机制的地基，它一旦破了，别人的查重结果就是错的。

**不要把「无指针」归因为 partial。** 对着 `archiver.ts` 看，图片下载失败时 `return` 发生在任何 `writeFile` 之前，`partial` **从不落盘**，所以磁盘上不可能存在「partial 留下的目录」。孤儿目录的真实来源是：写完数据、写指针之前中断（第 4 步与第 5 步之间）、`migrate` 删旧目录前中断（第 7 步）、手工复制、或旧版本行为。提示措辞保持中性，不替用户猜原因。

同理，**`note.json` 里的 `archive.status` 在磁盘上恒为 `complete`**（`archiver.ts` 写死，partial 那条路径根本不写文件），拿它判断完整性永远得到「完整」。完整性只能靠比对 `images[]` 与磁盘上真实存在的文件。

## 5. 数据来源与大数据量策略

前提：仓库当前几百篇，未来可能几万篇。要求是实现别太重。

### 5.1 成本在哪

| 动作 | 代价 |
|---|---|
| 列一个目录 | 低，但与条目数成正比。FSA 的异步迭代器逐条 yield |
| 读一个 `note.json` | 中。约 1~3 ms。1 万篇全读 = 十几秒 |
| 解码一张原图 | 高。原图 2~5 MB，解码后占内存十几倍 |

三者相差一到两个数量级，策略就是把工作尽量压到最便宜的那一档。

### 5.2 树的成本：O(笔记目录总数)，不是常数

要显示每个节点的篇数，就必须列出每个数据集叶子里的全部子目录名。**总工作量与仓库总笔记数成正比**，几万篇时首屏会有可感知的耗时。

采用的方案是**全量枚举一次，带进度，结果复用**：

- 建树时把每个叶子的子目录名数组一并留下，作为该叶子的 `NoteRef[]` 源。选中范围时直接从这份结果取，**不再列第二次目录**
- 建树期间顶栏显示进度（「正在读取目录 12 / 47」），树可以边建边出——中间层先显示，叶子的计数逐个填上
- 「重新加载」重跑这一过程

**为什么不是按需展开。** 按需展开（未展开的节点不显示计数）能让首屏恒定快，但根节点的「全部 479」就永远算不出来，而那个数字是核对数据集时第一眼要看的。全量枚举比读元数据便宜一到两个数量级，几万篇也就是秒级，配进度条可以接受。

**退路已经想好但不预先实现**：若实测下来某个仓库慢到不可接受，改为按需展开、未展开节点显示「—」而非数字。这是 UI 层的改动，核心层的 `buildTree` 已经是逐叶子产出的，改起来不动数据模型。

### 5.3 三层懒加载

1. **树**：只列目录名，不读文件（§5.2）
2. **范围**：选中节点 → 收集其下所有叶子的 `NoteRef[]`（`{noteId, datasetPath}`），直接复用建树时的结果。纯字符串，5 万条也就几 MB
3. **行**：滚进视口才读 `{datasetPath}/{noteId}/note.json`，一次拿全标题、作者、四个互动数、图片数、封面文件名、采集信息、正文与标签（后两者供搜索用）

默认排序是「数据集名倒序，组内按目录名」。日期形态的目录名天然就是时间倒序，零成本且稳定，不需要读任何文件就能定序。

**所有与磁盘内容对应的缓存，键必须是物理路径，不是 `noteId`。**

```ts
type NoteKey = string;   // `${datasetPath}/${noteId}`
```

理由：并发采集竞态（主文档 §6.4）的表现形式正是同一个 `noteId` 出现在多个 `datasetPath` 下，而浏览页恰恰要把这种情况显示出来。用 `noteId` 做键，先加载的那份会被另一个物理目录复用，落盘路径、采集者、图片、评论、质量提示全都会串。

用 `NoteKey` 的有：`RowState`、`NoteDetail`、评论数据、缩略图与原图 objectURL、读取失败状态。

按 `noteId` 索引的只有一处：`lookup()` 的结果缓存。它查的是索引而不是某个物理目录的内容，两者不能混用同一张表。

### 5.4 图片与缩略图

读封面文件 → `createImageBitmap(blob, {resizeWidth: 96, resizeQuality: 'low'})` → OffscreenCanvas → `convertToBlob` → objectURL。**原始 blob 立刻丢弃，只留 96px 那份**（行高 44px，96 是给 2x 屏留的余量）。

三种尺寸各自独立缓存，缓存键是 `${noteKey}::${file}::${size}`：列表行 96px、详情缩略图条 320px、看图器原图。

**两张表分开：缩略图 LRU 上限 300，原图 LRU 上限 3。** 原图一张几 MB，混进 300 条的表里会一直占着内存不放，而它只在看图器打开时需要。淘汰时 `URL.revokeObjectURL`。这是整个功能里唯一会吃内存的地方，不这么做撑不过几屏。切换范围、重新加载、组件卸载时释放全部。

读取走并发上限 6 的队列，滚出视口的任务在启动前丢弃；已经启动、无法真正中止的读取完成后结果被忽略并立即释放。

### 5.5 排序、搜索、采集者筛选：显式扫描

这三件事都需要当前范围的**全部**元数据，做不到懒加载。所以它们是显式的：点下去先弹一句「需要读取 128 篇」，带进度条和取消按钮（`AbortSignal`），扫完给该范围打上 `scanned` 标记。之后在同一范围里再排再搜是纯内存操作，瞬时。

扫描中途读失败的不中断，扫完汇总「N 篇读取失败」并可展开看是哪几篇。

**取消后已读到的元数据保留**（进 `Map`，下次扫描跳过已有的），但该范围**不**打 `scanned` 标记，因此排序/搜索仍需再扫一次——只是那次会快很多。不能拿半份数据去排序或搜索，否则用户看到的是一个没有说明的子集。

搜索匹配标题、正文、作者昵称、话题标签，大小写不敏感的子串匹配。不做分词、不做模糊匹配——这是团队内部核对用的工具，`includes` 足够。

**为什么不建持久缓存层。** 曾考虑开页全量扫描 + IndexedDB 缓存，让搜索排序瞬时。但 FSA 想做真正的增量更新得靠文件 mtime，而拿 mtime 必须 `getFile()`——等于还是把全库读了一遍，增量根本省不掉钱。结果是既背上缓存与磁盘对账的复杂度和 bug，又没换来开页速度。也曾考虑采集时顺手维护一份全库 `manifest.json`，但那直接推翻主文档 §4.2 的核心决策：单一文件多人写必然 Git 冲突。

### 5.6 树的判定规则

note_id 形态：`/^[0-9a-f]{16,32}$/`（实测真实 id 为 24 位小写 hex）。

遍历时先排除 `_index`、所有文件条目、所有 `.` 开头的目录。对剩下的每个目录 `D`，把它的子目录分成 `noteDirs`（名字符合形态）与 `otherDirs`：

- **`noteDirs` 非空 → `D` 是数据集叶子。** 计数 = `noteDirs.length`。`otherDirs` 全部忽略，并给这个叶子记一条质量警告「有 N 个非笔记子目录被忽略」。**不再往下递归**
- **`noteDirs` 为空 → `D` 是中间目录**，对每个 `otherDirs` 递归
- 递归后没有任何后代数据集的中间目录，不出现在树上（空目录因此自动消失）

**数据集不得再嵌套数据集**，这是刻意加的约束。放开它就要处理「一个目录既有笔记又有子数据集时篇数怎么算」，而那种目录结构本来就不该存在——采集器永远把笔记写在 `dataset_path` 的直接下级。

**判定只看名字，不去 `exists('note.json')` 验证。** 验证要对每个子目录多一次 IO，几万篇就是几万次。代价是形态正确但内容缺失的目录会走到列表里变成错误行，这比慢十几秒可接受。

对应的测试必须覆盖「笔记目录与脏目录混在同一层」，而不是分别测两种纯净情况——那正是旧版规则出错的地方。

### 5.7 外部改动

FSA 没有文件监听。`git pull` 拉来同事的新数据后页面不会自己知道。顶栏放一个「重新加载」按钮，点了清空内存缓存、重建树。

不做轮询——轮询等于每隔几秒把全库目录重列一遍，白烧 IO 换一个几乎用不上的实时性。

## 6. 模块划分

核心层不碰 DOM 和 chrome API，依赖全部注入，可在 Node 下跑 Vitest（沿用项目约定）。

### 6.1 存储接口

现有 `Store` 只有 `readText`，读不了图片二进制，也分不出文件和目录。两个都要补。

```ts
// core/read-store.ts —— 浏览页只认这个类型
export interface ReadStore {
  readText(path: string): Promise<string | null>;
  readFile(path: string): Promise<File | null>;
  exists(path: string): Promise<boolean>;
  listEntries(path: string): Promise<{ name: string; kind: 'file' | 'directory' }[]>;
}
```

`Store` 改为 `extends ReadStore`，`createStore` 补上 `readFile` 与 `listEntries` 的实现。既有的 `listDir` 原样保留，现有调用方不受影响。

**浏览页的所有模块，参数类型只写 `ReadStore`，绝不导入 `Store`。** 这是「只读」的真正保证——不是权限层面的，是模块边界层面的（§8.1）。测试用只实现 `ReadStore` 的 fake，任何隐藏的写依赖都会直接编译不过。

### 6.2 核心层新增

| 文件 | 职责 |
|---|---|
| `core/read-store.ts` | `ReadStore` 接口 |
| `core/browse/tree.ts` | `buildTree(readStore, onProgress)` → `DatasetNode[]`，逐叶子产出。判定规则见 §5.6 |
| `core/browse/scope.ts` | 节点 → `NoteRef[]`（复用建树结果）；`noteKeyOf(ref)`；各排序比较器 |
| `core/browse/row-meta.ts` | `loadNote(readStore, ref)` → `{ meta: RowMeta; detail: NoteDetail }` |
| `core/browse/comments.ts` | `loadComments(readStore, ref)` → 完整评论结构 + 配图相对路径 |
| `core/browse/quality.ts` | `checkQuality(readStore, ref, detail)` → §4.5 的状态判定 |
| `core/browse/search.ts` | 内存里的过滤与排序 |
| `core/browse/scan.ts` | `scanScope()`，§5.5 那套显式扫描的进度与取消 |
| `core/browse/types.ts` | 共享数据形状。`tree.ts` 与 `row-meta.ts` 互相需要类型，不抽出来会形成循环 import |
| `core/browse/virtual.ts` | `visibleRange(scrollTop, viewportHeight, rowHeight, total, overscan)`，纯函数 |
| `core/browse/lru.ts` | 泛型 LRU，淘汰时调注入的 `onEvict`。缩略图缓存的骨架 |
| `core/browse/queue.ts` | 并发上限队列，支持在任务启动前丢弃、启动后忽略结果 |

`visibleRange`、`lru`、`queue` 单独拎出来是因为它们是纯控制逻辑，恰好又是最容易出错和最主要的内存风险来源。做成不依赖 DOM 的模块才测得动（§9）。

### 6.3 数据形状

```ts
interface DatasetNode {
  path: string;          // 相对 root，如 collected/2026-08-03
  name: string;          // 末段
  isDataset: boolean;    // 叶子
  count: number;         // 候选笔记目录数（见 §4.2）
  noteIds: string[];     // 仅叶子有。建树时得到，选范围时直接复用
  ignoredDirs: string[]; // 仅叶子有。被忽略的非笔记子目录，用于质量警告
  children: DatasetNode[];
}

interface NoteRef { noteId: string; datasetPath: string }

type RowState =
  | { kind: 'pending' }
  | { kind: 'ready'; meta: RowMeta }
  | { kind: 'error'; reason: string };
```

`loadNote` 从**同一次** `note.json` 读取里同时产出两样东西，避免详情栏为了拿 `images[]` 把文件再读一遍：

- **`RowMeta`** —— 列表、搜索、排序要的：标题、正文、标签、作者昵称、四个互动数、图片数、封面文件名、`archive` 各字段、发布与编辑时间
- **`NoteDetail`** —— 详情栏要的：完整 `images[]`（画廊与缺失检查都需要）、作者完整信息、`ipLocation`、url

两者共用一个 `Map<NoteKey, ...>`，行加载时就把 `NoteDetail` 一并存下——多存的只是一个 `images[]` 数组，比多一次文件读取便宜得多。

**都不保留 `raw`。** 它是 `note.json` 里最大的一块，只为归档 diff 稳定性而存在。浏览页只从里面取 `ipLocation` 一个值，取完就丢；整份留在内存里几万篇会白吃几百 MB。

### 6.4 UI 层

新目录 `src/browser/`：`index.html` / `main.tsx` / `App.tsx`；组件 `Tree` `Table` `DetailPane` `Lightbox` `ScanProgress` `PermissionGate`；hook `useThumbnail`（把 `lru` 与 `queue` 接到真实的 `createImageBitmap` 与 `URL.createObjectURL` 上）与 `useScope`。

参数：行高 44px，overscan 8 行，缩略图并发 6，LRU 300。

### 6.5 样式

把 `src/sidepanel/panel.css` 里那套 token 抽到 `src/styles/tokens.css`，侧边栏与浏览页各自 import。深浅主题两套值本来就在里面，抽出来两边自动保持一致。

会改动到的现有代码只有三处：顶栏加按钮、`Store` 补两个方法、token 抽文件。

## 8. 错误处理与边界

### 8.1 权限，以及「只读」到底由谁保证

浏览页复用的是侧边栏用 `readwrite` 模式取得、存进 IndexedDB 的**同一个**句柄。对它调 `queryPermission({mode: 'read'})` 只是查询读权限的状态，**既不会撤销已有的 readwrite 权限，也不会返回一个降权后的新句柄**。所以不能说「浏览页从能力上就写不了」。

真正的保证来自模块边界：

- 浏览页的核心模块与组件，参数类型一律是 `ReadStore`（§6.1），不导入 `Store`
- 从 IndexedDB 取回句柄后用一个只暴露读方法的适配器包一层再往下传
- 测试里注入的 fake 只实现 `ReadStore`，有隐藏写依赖就编译不过

如果要操作系统层面的真只读，只能让用户再选一次 `mode: 'read'` 的句柄。那与「不在浏览页重选目录」的决策冲突，为一句措辞增加一道选目录流程不值得，不做。

权限门本身照旧：`queryPermission({mode: 'read'})` 不是 `granted` 就整页显示「授权访问数据仓库」按钮——`requestPermission` 必须由用户手势触发，页面加载时自动调用不会生效。从未配置过 root 时显示「请先在侧边栏选择数据仓库目录」。

### 8.2 单篇的问题不能拖垮整个列表

| 情况 | 表现 |
|---|---|
| `note.json` 缺失或 JSON 损坏 | 该行显示为错误行（note_id + 路径 + 原因），其他行照常 |
| 封面图文件不在 / 解码失败 | 占位图标，不算错误 |
| `comments.json` 不存在 | 详情栏显示「未采集评论」。这是正常状态，不是错误 |
| 图片文件少了几张 | 画廊对应位置占位，详情栏提示「N 张图片文件缺失」。若同时存在指向本目录的指针，按 §4.5 升级为「指针存在但数据不完整」 |
| 数据集目录里混进非笔记目录 | 按 §5.6 忽略，在该数据集节点上记一条质量警告，不报错 |
| 仓库还是空的 | 空态：「还没有采集过笔记」 |
| 扫描时几篇读失败 | 不中断，扫完汇总「N 篇读取失败」，可展开看是哪几篇 |

## 9. 测试策略

核心层全部用现有的 `tests/helpers/memory-fs.ts` 驱动，不需要浏览器。

**树与范围**

- 多级中间目录、只有 `_index` 的仓库、`.` 开头的目录被排除
- **笔记目录与脏目录混在同一层**（旧规则正是在这里出错的）
- 空目录不出现在树上；中间目录下全是空目录时整枝消失
- 叶子不再向下递归（笔记目录里的 `images/` 不会被当成子数据集）
- `noteIds` 被复用，选范围时不重复列目录

**元数据与详情**

- `loadNote` 一次读取同时产出 `RowMeta` 与 `NoteDetail`；两者都不含 `raw`；`ipLocation` 从 `raw` 提取成功
- 缺字段、JSON 损坏、文件不存在
- `loadComments`：正常、文件不存在、含子评论与配图
- `NoteKey` 隔离：同一 `noteId` 存在于两个 `datasetPath` 时，两行的元数据、路径、采集者互不污染（这条直接对应主文档 §6.4 的竞态）

**质量判定** —— §4.5 那张表的六种状态逐个覆盖，重点是「有指针但不指向当前路径」和「指针存在但数据不完整」

**搜索与排序** —— 标题/正文/作者/标签命中、大小写、各排序比较器与稳定性

**纯控制逻辑**（注入 fake loader 与 fake URL 工厂，不碰真实 canvas）

- `visibleRange`：首尾边界、总数为 0、overscan、容器高度变化
- LRU：到上限时淘汰最久未使用项并调用 `revokeObjectURL`；同一文件的 96px / 320px / 原图分属不同键；切范围、重新加载、卸载时全部释放
- 队列：滚出视口的排队任务不再启动；已启动、无法中止的任务完成后结果被忽略并立即释放
- 扫描取消：已读到的元数据保留，范围不打 `scanned` 标记

**只留给人工验收的**：真实图片能否解码、缩略图视觉质量、快速滚动帧率、DevTools 内存曲线、详情栏拖宽后刷新仍记得。这些在 Node 下要 mock 一整套 Web API，收益不抵成本。

## 10. 与既有决策的关系

本设计不推翻主文档任何已定决策：

- 不引入本地缓存层，磁盘仍是唯一真相源（主文档 §4.2）
- 不引入单一汇总文件（主文档 §4.2「为什么不用单一 index.json」）
- 不执行任何 git 命令
- 不写盘，因而与「指针存在 ⟹ 数据完整」不变量无关——但会把这个不变量被破坏的情况显示出来（§4.5）
