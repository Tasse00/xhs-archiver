# 小红书笔记归档插件

一个 MV3 Chrome 扩展。在小红书图文笔记页点击侧边栏按钮，即把该笔记的正文、标题、话题标签、互动数据、作者信息、全部图片、页面上已加载的评论与可选的文章级人工 Note，结构化归档到本地的 Git 数据仓库。

**当前状态：功能已实现，正在真实页面上做验收。**

## 解决什么问题

需要成规模采集小红书图文笔记做数据集时，手工保存图片、复制正文、记录互动数既慢又容易漏。多人协作时还要解决「这篇是不是有人采过了」。

本工具的取舍：

- **只采图文笔记**，视频笔记明确拒绝并说明原因
- **评论只采页面上已加载的那部分**，插件不滚动页面、不点「展开回复」、不构造 API 请求（理由见设计文档 13.1）。想多采就自己往下翻几屏再点采集；采到几条 / 共几条会直接显示在侧边栏
- **落到文件系统而非数据库**，数据仓库是个普通 Git 仓库，人能直接翻、脚本能直接读
- **跨采集者去重**，一篇笔记在仓库里始终只有一份。被他人采过时不另存一份，而是可以接管——接管后这篇归你，对方的指针被替换
- **为 Git diff 稳定性做了专门设计**，重采一篇的 diff 只显示互动数的变化，不是整块重写

## 安装

到 [Releases](https://github.com/Tasse00/xhs-archiver/releases) 下载最新的 `xhs-archiver-x.y.z.zip`，解压后在 `chrome://extensions` 打开开发者模式，点「加载已解压的扩展程序」，选中解压出来的文件夹。

完整步骤与首次使用配置见 [`INSTALL.md`](INSTALL.md)。

## 数据长什么样

数据仓库与本仓库**完全独立**——本仓库只有插件代码，采集数据放在你另外指定的目录。

```
<数据仓库根目录>/
├── .gitattributes                      插件首次初始化时生成
├── .gitignore
├── README.md                           目录约定、冲突处理、原图重取指引
├── _index/
│   └── 68/68a1b2c3d4e5f6/
│       └── zach.json                   指针：每篇每人一个文件
└── collected/                          默认写入路径
    └── 68a1b2c3d4e5f6/                 笔记 ID
        ├── note.json
        ├── annotation.txt               可选，文章级人工 Note
        ├── comments.json               读到评论时才有
        └── images/
            ├── 01.jpg
            ├── 02.jpg
            └── comments/               评论配图
                └── 6a6356e8…-01.webp
```

写入路径可在侧边栏修改。设置页给了四个快捷选项——`collected`、`collected/{今天}`、`{采集者}`、`{采集者}/{今天}`——点一下只是把它填进输入框，还要再点保存才生效。也可以自己填任意路径，例如按主题的 `collected/outfit`。插件不会自动改变已确认的路径：设成带日期的，第二天仍写在昨天那个目录里，需要时手动换。

查「这篇采过没」是一次目录读取，不需要扫全库。指针文件的存在即代表数据完整——写盘顺序保证了先有完整数据才有指针。

`annotation.txt` 是采集者对文章补充的多行纯文本 Note，属于文章而不是某个采集者。
重采、接管和迁移默认保留它；只有在侧边栏或浏览页主动修改或清空时才改变。
它不参与当前的搜索、筛选和排序。

## 几个关键设计

| 决策 | 原因 |
|---|---|
| File System Access API，不用 `chrome.downloads` | 只有它能**读回**目录，这是查重的前提 |
| 索引拆成「每篇一目录、每人一文件」 | 单一 `index.json` 在多人 Git 协作下必然冲突；拆开后永远是纯新增 |
| 图片走 Git LFS，仓库自建托管 | 存原图后 1000 篇约 4.2 GB，远超 GitHub LFS 免费额度 |
| 顶层 `url` 不带 `xsec_token`，另存 `share_url` | `url` 是笔记的稳定身份，`share_url` 是当下能点开的入口（token 会过期）；`file_id` 才是长期有效的图片凭据 |
| `note.json` 固定 key 顺序 + `raw` 递归排序 | 实测字段顺序在三种页面入口下不一致，不排序则换个入口重采就整块重写 |
| 时间戳固定 `+08:00` 偏移 | 用本地时区的话，不同时区的协作者会为同一时刻生成不同字符串 |
| `note.json` 的 `author` 采到悬浮卡片时才带简介、关注、粉丝、获赞与收藏 | 没采到时这组字段整个缺席，不写 `fans: 0` 之类的假值占位 |

## 技术栈

Vite 6 + @crxjs/vite-plugin 2 + TypeScript 5 + React 19 + Vitest 3。

核心层（`src/core/`）是纯 TypeScript，不接触 DOM 与 chrome API，依赖全部注入，可脱离浏览器单测。UI 层只订阅核心层状态。

```bash
npm install
npm test          # vitest
npm run build     # 产出 dist/，在 chrome://extensions 加载
npm run icons     # 重新生成图标，改了设计才需要跑
```

图标由 `scripts/gen-icons.mjs` 生成到 `public/icons/`（16/32/48/128 四档 PNG，外加一份 `icon.svg` 设计源）。脚本零依赖，自己做 SDF 光栅化而不是转 SVG——本机不一定有 `rsvg-convert`，而 16px 那档需要逐像素可控：48px 起画完整的「笔记卡片 + 盒盖 + 盒体 + 抠手」，16/32px 换一套只剩「卡片 + 托盘 + 一道红缝」的简化几何，否则细节窄于一个物理像素，只会糊成一层灰雾。**改设计请改脚本再重跑，不要手改 PNG。**

## 迭代范围

- **v1**：设置引导、页面识别、查重、单篇采集、评论采集、视频拒绝、失败重试
- **v2**：采集历史列表、手动批量查重
- **v3**：统计面板、CSV/JSONL 导出、全仓重复项扫描

v2 与 v3 只新增 UI 视图并复用核心层的遍历聚合能力，核心层不改动。
